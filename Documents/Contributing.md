# Contributing

Read these rules carefully before opening a pull request.

## 1. AI Code and Responsibility
You may use AI/LLM tools to assist with writing code, documentation, or tests. However, **you own every single line you submit**. If generated code introduces memory corruption, undefined behavior, resource leaks, or crashes, you take full responsibility. Read, understand, and verify every line before submitting.

## 2. Sign Off Your Commits (DCO)
Sign off every commit using the `-s` flag:

```sh
git commit -s -m "subsystem: short description of change"
```

Pull requests containing unsigned commits will be rejected.

## 3. Code Style & Standards
- **Language:** Pure **C99** (`-std=c99`). No C++ features, no compiler-specific extensions without guarded fallbacks.
- **Zero Warnings:** All code must compile cleanly under `-Wall -Wextra -Werror -pedantic` (GCC/Clang) and `/W4 /WX` (MSVC).
- **Formatting:** Follow the repository's `.clang-format` and `.editorconfig`. Run `clang-format` before committing.
- **Amalgamation Discipline:** Edit only modular files inside `include/` and `src/`. Do **not** manually edit the amalgamated single-header output in `dist/`—it is auto-generated by the amalgamation tool.

## 4. Test Everything Before Submitting
Build both the modular library and the amalgamated single-header version. Run the test suite and examples. Confirm your changes work and verify you did not break existing behavior or cross-platform builds (Linux & Windows). Broken builds or untested code will result in immediate PR closure.

## 5. Describe Your Changes
Write a clear, concise description for your pull request. State **what** was changed, **why** it was changed, and **how** it was tested. Empty or vague pull request descriptions will be closed.

## 6. Keep Pull Requests Small
One pull request covers one bug fix, one feature, or one focused cleanup. Keep diffs minimal and easy to review. Do not submit massive PRs rewriting unrelated subsystems at once.
